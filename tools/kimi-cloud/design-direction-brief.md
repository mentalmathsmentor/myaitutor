# 1. Context & Conditions

Act as a cautious, meticulous interface design reviewer. The product owner wants a striking, futuristic MyAITutor website: a fictional teacher overview, editable lesson plan, learner practice and useful review. A previous candidate used a conventional blue teaching dashboard. There is no live backend or student data. This is an independent design direction check before comparing implementations; you are not inspecting a finished candidate.

# 2. Help & Hands

Use only this brief. No tools, browsing, execution, private data, account access or further agents. State what evidence you cannot inspect. Consider visual composition, purposeful motion, interaction completeness, accessibility and frontend weight as distinct review angles.

# 3. Objective & Output

Return a concise design specification that could guide a working frontend. Make one coherent, distinctive visual concept with a memorable opening composition, a useful spatial or timeline interaction and transitions connecting overview, planning and practice. Specify typography, colour roles, materials, hierarchy, states and motion. Describe the main teacher-to-practice-to-review journey and what each meaningful control does. Propose three concrete details likely to make the result memorable without creating visual clutter. Include brief CSS or interaction pseudocode only when it clarifies an effect; do not return a whole untested application.

Keep the experience practical for teachers and learners. A mentor, if proposed, must be optional and suitable for a naturalistic adult avatar; do not fabricate a realistic asset or substitute an anime character. Prefer lightweight CSS, SVG and native transitions. Include mobile and reduced-motion variants. A futuristic aesthetic must retain readable text, visible focus and useful empty/error/success states. Do not simulate live AI, curriculum certification, compliance or real learning results.

# 4. Role & Rules

Make no external calls and perform no publication or deployment. Do not infer facts about a finished implementation or claim tests ran. Give conclusions, a concise design rationale and an observable test plan; do not expose private reasoning. The controller enforces the separately approved single-call token, cost, timeout and no-retry limits.

# 5. Evaluation & Examples

Check your proposal for internal consistency: visual novelty serves navigation; motion communicates state; mobile controls remain usable; reduced motion still conveys the same transitions; dependency cost has a clear purpose. Give acceptance checks for keyboard navigation, state restoration, practice feedback, horizontal overflow, console errors and asset weight. Identify the largest tradeoff. Distinguish a proposed design from verified behaviour.

# 6. Show & Suggest

Audience: the product owner and controller. Return a readable design specification in the response, ending with one to three ranked implementation suggestions grounded in the proposed interaction and performance tradeoffs. The controller compares this direction with the separate coding candidate after it exists. No change to an application or production environment is authorised by this response.
